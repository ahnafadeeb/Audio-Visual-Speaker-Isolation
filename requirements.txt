# Audio-Visual Speaker Isolation — main application environment
# Python 3.12 ONLY.  (numpy 1.26.4 has no cp313/cp314 Windows wheel, and
#  mediapipe 0.10.21 — the last release with mp.solutions.face_mesh — tops out
#  at cp312 as well.)
#
# Install torch FIRST, from the CUDA index, then this file:
#
#   py -3.12 -m venv .venv
#   .venv\Scripts\activate
#   pip install torch==2.11.0 torchaudio==2.11.0 --index-url https://download.pytorch.org/whl/cuXXX
#   pip install -r requirements.txt
#
# >>> PICK cuXXX BY GPU GENERATION -- THIS IS NOT INTERCHANGEABLE. <<<
#
#   Ada / Ampere / Blackwell (RTX 30xx, 40xx, 50xx)  ->  cu128
#   Pascal (GTX 10xx, sm_61)                         ->  cu126
#
# Both indexes carry the torch 2.11.0 + torchaudio 2.11.0 cp312-cp312-win_amd64
# pair, so the pin below is unaffected either way -- only the CUDA build differs.
#
# Why it matters: `torch.cuda.is_available()` returning True does NOT mean the
# wheel can run on your card.  It proves a driver and runtime exist, nothing
# more.  A wheel lacking your GPU's compute capability imports fine, reports
# CUDA available, allocates memory -- then dies at the first real kernel launch
# with "no kernel image is available for execution on the device", minutes into
# a job, from inside SepFormer, looking like a model bug.  PTX JITs *forward*
# from a lower arch, never backward, so a too-new wheel has no path to run.
#
# MEASURED on 2026-08-11 via `torch.cuda.get_arch_list()`:
#   cu126 -> sm_50 sm_60 sm_61 sm_70 sm_75 sm_80 sm_86 sm_90
#   cu128 -> drops the Pascal/Maxwell tail, adds sm_100/sm_120 (Blackwell)
#
# So cu126 has sm_61 natively (verified: real SASS, no JIT, all of matmul /
# fp16 / conv1d / SDPA launch on a GTX 1050 Ti).  It has no sm_89, so an Ada
# laptop GPU runs it through sm_86 SASS -- functional but not its native path,
# which is why cu128 remains correct for the demo machine.
#
# Verify on ANY new machine before trusting it:
#
#   .venv\Scripts\python.exe scripts\gpu_probe.py
#
# VERIFIED against the PyPI JSON API and download.pytorch.org on 2026-08-11:
#   * torch ships up to 2.13.0; torchaudio stops at 2.11.0 (maintenance mode).
#     2.11.0 is therefore the newest MATCHED pair.  Mismatched torch/torchaudio
#     produces "ImportError: DLL load failed" on Windows, which reads like a CUDA
#     fault and will cost you a day.  Do not "upgrade torch".
#   * cu128 carries torch 2.11.0 AND torchaudio 2.11.0 as cp312-cp312-win_amd64.
#     (cu129 tops out at 2.9.0 — do not use it.  cu130 also has the 2.11.0 pair
#     if you are on a driver new enough to want it.)
#   * cu126 carries the same pair, and is the newest index that still builds
#     sm_61.  cu118/cu121/cu124 do NOT have 2.11.0 at all (they top out at
#     2.7.1 / 2.5.1 / 2.6.0 for cp312), so "use an older CUDA for an older card"
#     costs you the matched pair as well.

# --- vision -------------------------------------------------------------------
# 0.10.21 is the LAST release exposing mp.solutions.face_mesh (removed in 0.10.3x),
# and the last with per-interpreter win_amd64 wheels (cp39/310/311/312).
mediapipe==0.10.21
#
# >>> THE JAX TRAP — this pin is load-bearing, do not remove it. <<<
# mediapipe 0.10.21 declares `numpy<2` but depends on **unpinned** `jax`.
# Verified on PyPI: jax 0.7.2 and later require numpy>=2.0 (0.11.0 wants >=2.1).
# So a plain `pip install mediapipe==0.10.21` resolves jax to a modern release,
# which drags in numpy 2.x, which contradicts mediapipe's own numpy<2 and either
# hard-fails the resolver or — worse — succeeds and leaves you with a numpy that
# mediapipe cannot import.  jax 0.7.1 is the LAST version compatible with
# numpy 1.26.4.  jaxlib must be exactly version-paired (jax 0.7.1 requires
# jaxlib>=0.7.1,<=0.7.1); both have cp312-cp312-win_amd64 wheels.
jax==0.7.1
jaxlib==0.7.1
#
# mediapipe also requires protobuf<5,>=4.25.3.  That range resolves to 4.25.9,
# which has a cp310-abi3-win_amd64 wheel (abi3 covers 3.12) plus a py3-none-any
# fallback, so it installs cleanly.  Left unpinned so pip picks the newest 4.25.x.
#
# >>> OPENCV DISTRIBUTION COLLISION <<<
# mediapipe depends on `opencv-contrib-python`, NOT `opencv-python`.  Both ship
# the same top-level `cv2` module; installing both makes the import order decide
# which one wins, and the loser's files are silently overwritten.  app/vision.py
# only uses core cv2 (VideoCapture, CascadeClassifier), which contrib provides a
# superset of — so we depend on contrib alone and let mediapipe's requirement be
# satisfied by the same package.  Do NOT add opencv-python back.
opencv-contrib-python>=4.9,<4.11
